# Stage 3.0 基础模型选型基准报告：本地 Ollama 多上下文吞吐与显存实测

> **归档日期**：2026-11-23  
> **阶段定位**：作为 [stage3_nextgen_graphrag_plan.md](stage3_nextgen_graphrag_plan.md) 的前置基础设施（**Stage 3.0**），本报告在 8 GB 消费级独立显存环境下对三款本地候选模型（`gemma4:12b`、`qwen3.5:9b`、`qwen3.5:4b`）进行了跨上下文窗口（4k → 128k）的 Prefill/Decode 吞吐、首字延迟（TTFT）与物理显存实测，正式确立第三阶段 GraphRAG 管线的底层基础模型与推理参数基线。

---

## 1. 核心选型决策（Executive Summary）

| 角色定位 | 选定模型 | 关键运行参数 | 典型吞吐（16k RAG） | 峰值显存 |
|---|---|---|---|---:|
| **Stage 3 主力基础模型**（在线 GraphRAG / CoT / ToT / Multi-Branch / LLM-Judge） | **`qwen3.5:9b`** (Q4_K_M) | `ollama_native`、`think=false`、`num_ctx=16384`（按需最大 `32768`）、**`num_gpu=99`** | Prefill **2,343 t/s** / Decode **51.3 t/s** | **6,746 MiB**（32k: 7,274 MiB） |
| **高吞吐辅助模型**（离线 KG 三元组抽取 / Query 改写 / 轻量路由 / 高频多跳探索） | **`qwen3.5:4b`** (Q4_K_M) | `think=false`、`num_ctx=4096~16384`（默认即全 GPU，128k 需 `num_gpu=99`） | Prefill **3,838 t/s** / Decode **77.4 t/s** | **4,252 MiB**（4k: 3,762 MiB） |
| **可选对照模型**（低频短上下文精排 / 消融基线） | **`gemma4:12b`** (Q4_K_M) | `think=false`、`num_ctx ≤ 16384`、**严禁设置 `num_gpu=99`** | Prefill **1,075 t/s** / Decode **22.5 t/s** | **6,748 MiB**（含 CPU 卸载） |

**三大核心工程发现**：
1. **显式 `num_gpu=99` 释放 `qwen3.5:9b` 1.36×–5.77× 长上下文红利**：Ollama 0.40.17 的默认显存估算器在 8 GB 显卡上过度保守（约 ~6.35 GiB 即停止 GPU 分配并将层提前切回 CPU），导致 `qwen3.5:9b` 从 `8k` 起即掉速、`32k` 跌至 19.1 t/s。显式设置 `GRAPHRAG_LLM_NUM_GPU=99` 后，其在 **4k–64k 全程 100% GPU 运行**，32k Decode 跃升至 **48.7 t/s（2.55×）**。
2. **Qwen 3.5 混合注意力架构带来极低 KV Cache 斜率**：实测 `qwen3.5:9b` 与 `qwen3.5:4b` 的全 GPU 峰值显存随上下文窗口严格线性增长，斜率仅 **~33 MiB / 1k tokens**（远低于传统全注意力 9B 模型），使 8 GB 显存首次具备流畅支撑 16k–32k 甚至 64k GraphRAG 的硬件可行性。
3. **`gemma4:12b` 在 8 GB 显卡上存在物理显存天花板**：其磁盘权重已达 8.0 GB，超过物理可用显存（7.96 GiB）。强设 `num_gpu=99` 会触发 Windows WDDM 共享显存经 PCIe 换页，导致 16k Prefill 暴跌 **-82%**（1075 → 198 t/s）、Decode 暴跌 **-68%**（22.5 → 7.3 t/s）。

## 2. 测试环境与方法论

- **测试硬件**：NVIDIA GeForce RTX 5060 Laptop GPU（**8,151 MiB ≈ 7.96 GiB** 物理显存，Driver 621.01）、Intel Core Ultra 7 251HX、31.5 GB RAM、Windows 11。
- **推理引擎**：Ollama `v0.40.17`（默认环境变量，未启用实验性 KV 量化）。
- **控制变量**：
  - 统一 `think=false`（与本项目 `GRAPHRAG_LLM_THINK=false` 对齐）、`temperature=0`、`seed=42`、`num_predict=256`。
  - 每次请求在 `system` 提示词最前部注入唯一随机 `[run:<nonce>]`，彻底阻断 Ollama 前缀 KV Cache 复用，确保 Prefill 速度真实反映无缓存 RAG 检索场景。
  - 每个场景前强制卸载全部模型并等待显存归零，隔离冷加载耗时与当前 `num_ctx` 的独立峰值显存；`4k–32k` 跑 2 轮取热态中位数，`64k–128k` 跑 1 轮。
  - 显存以 `nvidia-smi` 每 250ms 采样整卡 `memory.used` 峰值为准，同时记录 `/api/ps` 的 GPU 分配比。（注：Ollama 0.40.17 对 `gemma4:12b` 的 `/api/ps` 存在统计低报 Bug，故以 `nvidia-smi` 实测为准。）

| `gemma4:12b` | `gemma4` | 11.9B | Q4_K_M | 8.0 GB | 1.447 |

## 4. 显存需求建模与 Embedding 共存约束

基于全 GPU 实测值，两款 Qwen 3.5 模型的物理显存占用（含 CUDA context 与运行期工作缓冲）可精确估算为：

- `qwen3.5:9b`：$\text{Peak VRAM} \approx 6218 + 33.0 \times \text{ctx\_k}\ \text{MiB}$
- `qwen3.5:4b`：$\text{Peak VRAM} \approx 3650 + 32.8 \times \text{ctx\_k}\ \text{MiB}$

在 **8 GB 物理显存** 下，结合 Stage 3.1 即将接入的本地稠密 Embedding（`nomic-embed-text` ~0.4 GiB / `bge-m3` ~1.2 GiB），显存治理策略定为：

1. **安全显存红线**：Windows 桌面环境保留 ≥ 750 MiB 余量（即 LLM + Embedding 合计 ≤ 7,400 MiB），严防触发 WDDM 共享显存换页。
2. **默认线上配置**：`qwen3.5:9b` + `num_ctx=16384` + `num_gpu=99`（~6,746 MiB）可与轻量 `nomic-embed-text`（~400 MiB）平稳共存；若接入 `bge-m3`（~1.2 GiB），离线批量索引阶段单独跑 Embedding，或在线查询阶段将 Embedding 固定在 CPU / 使用 `OLLAMA_FLASH_ATTENTION=1` + `OLLAMA_KV_CACHE_TYPE=q8_0` 压缩 KV Cache。
3. **禁止盲目全局预留超大 `num_ctx`**：`reserve32k_short` 证明静态预留大窗口会直接锁定对应 KV 显存并在默认调度下拖垮短问答吞吐（`qwen3.5:9b` 56.1 → 28.8 t/s）；后续各阶段应按需设定 `num_ctx`（建图抽取 `4k–8k`，在线 RAG `16k`，全局超长汇总按需 `32k`）。

### 6.3 工业故障诊断实时 `PPR + ToT` 回归

- 实跑多症状并发离心泵故障诊断耗时 **`26.1s`**（含冷加载与 3 路分支校验），Compact 三级压缩 `3,143 → 508 tok (-83.8%)`，精准选中 `H1: 轴系不对中 (0.87, G:0.76 S:0.95)` 并剪枝 `H3: 三相异步电机 (0.79)` 与 `H2: 滚动轴承 (0.60)`，**`GroundingAudit = 100.0% (3/3 steps, passed=True, ungrounded=0)`**。
